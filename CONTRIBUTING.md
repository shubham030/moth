# Contributing to moth

moth is small on purpose: a ~1.7k-line VM, a ~1.5k-line renderer (`wc -l`
over each one's implementation files), a compiler, and a widget framework,
each behind a documented contract. Most changes touch
one of them and can be built, tested and verified without hardware.

## Build and run

```console
$ make vm            # VM + mothrun (headless) + mothsim (SDL window)
$ make test          # the whole suite — compiler goldens, renderer budgets,
                     # crypto vectors, push policy, serial, widget contracts
$ make ui F=examples/ui/pomodoro.dart    # compile and run one app in a window
$ make blink         # the smallest end-to-end path, no hardware
```

Board work needs ESP-IDF 5.4 (`ui/esp-s3`); everything else needs CMake, a C
compiler, SDL2 and a Dart SDK.

## The test culture

`make test` must be green before every commit, and the suite is built so that
green means something:

- **The language is tested against Dart itself.** Golden cases in
  `test/cases/` have expectations generated by running the same program on
  the real Dart SDK — the suite asserts moth matches Dart, not that moth
  matches its own past behavior.
- **Regression tests are mutation-checked.** When a test guards a fix, we
  re-introduce the bug and confirm the test fails. A test that cannot fail
  is treated as a bug in the test.
- **Performance is a budget, not a hope.** `make render-test` asserts
  pixels-visited budgets per frame ([docs/PERF_REVIEW.md](docs/PERF_REVIEW.md)
  explains what a failure means). Frame-rate claims come from `make fps` on a
  real board — never from anywhere else.
- **Contracts have contract tests.** The renderer's behavior
  ([docs/BACKEND.md](docs/BACKEND.md)) and the push protocol's accept/reject
  policy are pinned by tests that drive the real implementations — sockets,
  pixels, and all.

If your change adds a guarantee, add the test that would catch its removal.

## How changes are reviewed

Every review finding gets an explicit disposition, stated in the commit
message or the review reply:

- **Fixed** — after reproducing the failure, or constructing it in a test.
- **Rejected** — with evidence: the code, a measurement, or the documented
  semantics the finding contradicts.
- **Deferred** — consciously scoped out, with the reasoning recorded
  (usually in [docs/DECISIONS.md](docs/DECISIONS.md)) so it gets revisited
  deliberately rather than forgotten.

Never loosen a guarantee, a budget, or a documented behavior just to make a
finding go away.

## Docs are part of every feature

The website serves `docs/` directly, and the landing page carries an honest
status section whose whole value is being true. Before a feature branch is
done, sweep:

- `docs/ROADMAP.md` — checkboxes and measured numbers
- `docs/getting-started.md` — if the feature changes what a new user does
- `docs/how-it-works.md`, `docs/language.md`, `docs/hardware.md` — any page
  describing the touched area
- `website/src/pages/index.tsx` — status columns and feature cards

A claim the code no longer backs is a bug, whichever file it lives in.

## Hard constraints

- **Never read or write LVGL's XML format.** Its spec license excludes
  third-party OSS tooling ([ADR-002](docs/DECISIONS.md)). The MIT C API was
  fine to use; the XML never is. This applies to tooling, tests and docs.
- **No invented numbers.** Performance figures come from `make fps` and the
  profiling hooks; sizes come from measuring the artifact. If it wasn't
  measured, it isn't claimed.
- **The out-of-box path stays secret-free.** A first program must compile,
  run and push over the cable without accounts, tokens or configuration.

## Commit style

Conventional commits (`feat:`, `fix:`, `docs:`, `perf:`, ...), imperative
subject under 72 characters, and a body that explains *why* — the constraint
or measurement that motivated the change, not a play-by-play of how it was
found.
